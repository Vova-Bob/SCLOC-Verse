# Settings Hub — Центр керування налаштуваннями

> Єдиний центр налаштувань SCLOC-Verse з навігацією за функціональними категоріями.
> Картка-індекс: KB §17.7. Архітектурне рішення: ADR-009. Макети: `.kilo/settings-mockups/`.

## Контекст

* **Поточний стан.** Усі налаштування живуть в одному `SettingsCanvas.xaml` (514 рядків, code-behind) — плоский список: шлях до гри, провідник/автопошук/очистити кеш, канал оновлень, менеджер версій, 4 чекбокси. З ростом кількості параметрів (overlay, гарячі клавіші вже існують як окремі UI-шари) єдина сторінка стає незручною.
* **Проблема.** Категоризація за інструментом («налаштування Hangar Timer», «налаштування Anti-AFK») дублює логіку та ламається при появі нових інструментів. Глобальні налаштування (шлях, автозапуск, трей) змішуються з приватними (overlay, hotkeys). Відсутня точка входу для майбутньої синхронізації профілю (Supabase).
* **Що мотивувало.** UX First: користувач має знайти параметр за <30с. Функціональна декомпозиція відповідає реальній структурі застосунку (Загальне → Гра/Оновлення/Обслуговування; Гарячі клавіші → існуючий `HotkeyService`; Overlay → існуючий `HangarSettingsService`).
* **Evidence.** `SettingsService` реалізує `ISettingsService` + `IUpdateChannelService` + `IPreferencesService` (machine-specific `Settings.Default`). `HotkeyDefinition` вже несе `DefaultGesture`/`CurrentGesture`/`VisibleInUi`/`Description` + `HotkeyConflictPolicy` — інфраструктура конфлікт-виявлення існує. `HangarSettingsService` (X/Y/scale/opacity) — persistence overlay.

## Принципи дизайну

1. **Категорії за функцією, не за інструментом.** «Загальне», «Гарячі клавіші», «Overlay» — а не «Hangar Timer», «Anti-AFK».
2. **Немає передчасних категорій.** Категорія існує лише коли має критичну масу налаштувань. Зарезервовані категорії показують плейсхолдер, а не вигадані поля.
3. **Контент лише для реалізованого функціоналу.** Анти-AFK без overlay → показуємо «інструмент не активний», не фабрикуємо повзунки.
4. **Миттєве збереження без Apply.** Зміна → запис одразу. Мітка «•» біля зміненого пункту.
5. **Reset у межах своєї категорії або контролу.** Глобального «Скинути все» немає.
6. **Головна (Home) — швидкий доступ / статус, не налаштування.**

## Цільова структура навігації

| Категорія | Стан (Phase) | Призначення |
|---|---|---|
| **Головна** | reserved | Швидкий доступ / статус синхронізації |
| **Загальне** | ✅ Phase 0 | Star Citizen шлях, автозапуск, трей, автооновлення локалізації, канал, менеджер версій, очистити кеш, розширена діагностика |
| **Локалізація** | reserved | Майбутнє: керування перекладами (зараз частина Загальне) |
| **Інтерфейс** | reserved | Майбутнє: тема, мова застосунку, масштаб UI |
| **Гарячі клавіші** | ✅ Phase 0 | 14 дій з `HotkeyService`, конфлікт-UX, per-category reset |
| **Overlay** | ✅ Phase 0 | Типи оверлеїв (Hangar Timer активний, Anti-AFK не активний): масштаб/прозорість/позиція |
| **Профіль** | reserved | Майбутнє: синхронізація Supabase, резервна копія, експорт/імпорт `profile.json` |
| **Про програму** | reserved | Версія, ліцензія, посилання |

**Вилучені категорії** (див. KB §15.3.1):
- `Діагностика` → чекбокс «Розширена діагностика» живе у Загальне.
- `Поведінка` → згорнуто у Загальне.
- `Оновлення` → згорнуто у Загальне.

## Мета (Acceptance Criteria)

### Загальні AC (весь Hub)
* **AC1:** Hub відкривається з головного вікна (іконка ⚙) та клавішею `F1` **лише при активному вікні SCLOC-Verse** (не глобально).
* **AC2:** Ліва панель — навігація (8 пунктів); активна категорія підсвічується; зарезервовані категорії доступні, але показують плейсхолдер.
* **AC3:** Миттєве збереження: зміна контролу → запис у persistence без кнопки «Застосувати»; мітка «•» біля зміненого.
* **AC4:** Немає глобального «Скинути все». Reset існує лише per-category (унизу категорії) та per-control (↺ біля поля).
* **AC5:** Українські тексти UTF-8 без mojibake у всьому Hub (P0).
* **AC6:** Build: 0 warnings, 0 errors. Zero Regression: існуючі `SettingsService`/`HotkeyService`/`HangarSettingsService` контракти не змінено.

### AC: Загальне (Phase 0)
* **AC-G1:** Шлях до гри = `...\StarCitizen` (не `\LIVE`); середовища (LIVE/PTU/EPTU/TECH-PREVIEW) — read-only індикатори автовизначення, не перемикачі.
* **AC-G2:** Опис шляху: «Використовується для встановлення локалізації та конфігурації.»
* **AC-G3:** Кнопки: «Огляд…», «Автопошук», ↺ (скинути шлях до типового). Немає кнопки «Провідник».
* **AC-G4:** Чекбокси: Автозапуск із Windows, Згортати в трей, Мінімізувати при запуску гри, Автооновлення локалізації, Розширена діагностика — через існуючий `IPreferencesService`.
* **AC-G5:** Канал оновлень (Stable/Beta/Dev) через `IUpdateChannelService`; «Менеджер версій…» відкриває існуючий діалог.

### AC: Гарячі клавіші (Phase 0)
* **AC-H1:** Список 14 дій з `HotkeyService`, згрупований за категоріями (Застосунок / Hangar Timer / Overlay·масштаб).
* **AC-H2:** Тільки `HotkeyDefinition.VisibleInUi==true` показуються.
* **AC-H3:** Клік на комбінацію → режим вводу; `Esc`/`Backspace` очищає; повторне використання існуючого жесту іншою дією → діалог конфлікту (Скасувати / Перевизначити).
* **AC-H4:** Per-item reset (↺) повертає `CurrentGesture=null` (→ `DefaultGesture`); per-category reset скидає всі.

### AC: Overlay (Phase 0)
* **AC-O1:** Список типів оверлеїв; Hangar Timer — активний (має налаштування); Anti-AFK — плейсхолдер «інструмент не активний».
* **AC-O2:** Для активного оверлея: масштаб, прозорість, позиція (X/Y) через `HangarSettingsService`.
* **AC-O3:** Позиція маркована «службові» — змінюється перетягуванням на оверлеї, тут лише читання/точний ввод.

## Варіанти рішення (Decision Engine — architectural, ≥3)

### Варіант A: Залишити єдиний `SettingsCanvas`, додати секції-розриви
* **Опис.** Не створювати нову оболонку; розділити існуючу сторінку візуальними розділювачами + заголовками секцій.
* **Плюси.** Zero Regression максимальний; мінімум коду; найменший ризик.
* **Мінуси.** Сторінка росте → scroll-purgatory; зарезервовані категорії (Профіль/Локалізація) не мають природного місця; немає швидкої навігації; порушує UX First (<30с пошук).
* **Ризики.** При додаванні overlay- та hotkey-налаштувань у цю сторінку вона перевантажується.

### Варіант B: Settings Hub — нова оболонка з лівою панеллю-навігатором ✅
* **Опис.** Окрема логічна оболонка (лівий rail категорій + права панель вмісту); категорії за функцією; зарезервовані категорії з плейсхолдерами.
* **Плюси.** Масштабована декомпозиція; швидка навігація; точка входу для Профілю/синхронізації; відповідає принципу «категорії за функцією»; кожна категорія — окремий Canvas (Reuse Canvas-патерну ADR-006).
* **Мінуси.** Більше коду/XAML; потрібно керувати станом «активна категорія».
* **Ризики.** Відхиляння від існуючого стилю автора — мітігується: макети затверджені, стиль палітри з `Styles.xaml`.

### Варіант C: Діалог із вкладками (TabControl)
* **Опис.** `Window` з `TabControl` угорі — вкладки = категорії.
* **Плюси.** Стандартний WPF-патерн; швидка навігація.
* **Мінуси.** Вкладки погано масштабуються (8 категорій → перенесення вкладок); менш гнучкий layout; не відповідає «Control Center»-метафорі; зарезервовані категорії виглядають як порожні вкладки.
* **Ризики.** Обмежена вертикаль для росту; конфлікт зі стилем застосунку.

## Рекомендоване рішення

**Варіант B (Settings Hub).** Обґрунтування:
- **Reuse First:** категорії реалізуються як окремі Canvas (ADR-006 Canvas-підхід), навігація через розширення `CanvasManager`. Hotkeys-категорія споживає існуючий `HotkeyService` + `HotkeyConflictPolicy`. Overlay — `HangarSettingsService`. Загальне — `ISettingsService`/`IUpdateChannelService`/`IPreferencesService`. Жодного нового сервісу для Phase 0.
- **UX First:** ліва панель дає <30с пошук; зарезервовані категорії явно марковані.
- **Evolution over Revolution:** не переписує Settings-сервіси, лише додає UI-шар композиції над ними.
- **Точка зростання:** Профіль/`profile.json` отримує природний дім.

## Зона впливу

* **Нові файли:** `Controls/SettingsHub/SettingsHubCanvas.xaml(.cs)` (оболонка + навігація); Canvas-и категорій `SettingsHub/General/`, `SettingsHub/Hotkeys/`, `SettingsHub/Overlay/` (+ reserved placeholders).
* **Існуючі файли (розширення, не перепис):** `MainWindow.xaml(.cs)` — точка входу в Hub (⚙ + F1-хендлер при активному вікні); `AppCompositionRoot` — реєстрація Hub-Canvas.
* **Сервіси:** БЕЗ ЗМІН контракту `ISettingsService`/`IUpdateChannelService`/`IPreferencesService`/`IHotkeyService`/`IHangarSettingsService`. Hub лише споживає.
* **Схема БД:** не зачіпається (Phase 0).
* **Контракти:** `SettingsCanvas.xaml` замінюється Hub (старий Canvas виводиться з експлуатації після міграції контенту).

## Ризики та мітігація

| Ризик | Мітігація |
|---|---|
| F1 як глобальна гаряча клавіша конфліктує з ігровою/системною допомогою | F1 спрацьовує **лише при активному вікні SCLOC-Verse**, не глобально (Window-фокус-чек перед відкриттям) |
| Втрата існуючих налаштувань при міграції SettingsCanvas → Hub | Reuse сервісів; persistence не змінюється; приймальні тести кожного параметру (AC-G1..G5) |
| Mojibake українського тексту (P0) | Усі XAML UTF-8; build + візуальна перевірка; правило кодування AGENTS.md |
| Зростання MainWindow (TD-6 God Class) | Hub як окремий Canvas; логіка входу — тонка; бізнес-логіка в категоріях/сервісах |

## Quality Gates

* **Core:** Root Cause (плоский список → нездатність масштабуватись), Zero Regression (сервіси не чіпаємо), Evidence (затверджені макети + кодові контракти), UTF-8.
* **Extended:** Integration First (точки входу: MainWindow ⚙/F1 + CanvasManager + AppCompositionRoot). Security Review **не потрібне** (UI/локалізація; не Auth/Installer/Network/SQL).

## План реалізації (Phases)

* **Phase 0:** Hub-оболонка + Загальне + Гарячі клавіші + Overlay. Миграція контенту з `SettingsCanvas`. Зарезервовані категорії — плейсхолдери.
* **Phase 1:** Профіль — `profile.json` (локальний контракт/схема-версія), експорт/імпорт.
* **Phase 2:** Профіль — опціональна синхронізація Supabase (hotkey-bindings, overlay-налаштування; **не** hotkey-події — L3 Local Only).
