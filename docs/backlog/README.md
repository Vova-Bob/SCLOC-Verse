# docs/backlog/ — деталізація великих задач

> **SEW (SCLOC-Verse Engineering Workflow).** Норматив: [`AGENTS.md`, розділ «docs/backlog/ — деталізація великих задач»](../../AGENTS.md).

## Призначення

Для великих задач, специфікація яких не вміщується в картку KB §17 (Backlog), створюється окремий Markdown-файл у цій директорії. Knowledge Base §17 залишається **індексом** (короткі картки з посиланнями), а деталі живуть тут.

Це аналогічно до того, як `docs/observability/` зберігає детальні forensic-документи, а KB — лише індекс (§18.1 Cross References).

## Коли створювати файл у backlog/

* Специфікація задачі > ~50 рядків (не вміщується в картку KB).
* Задача має складний Design з кількома варіантами рішення.
* Потрібне збереження контексту між сесіями (аналіз залежностей, дослідження альтернатив).
* Задача розбивається на підзадачі AC1/AC2/AC3...

**Не створювати** файл для:
* тривіальних правок (опечатка, UI-твік);
* задач, що повністю описуються карткою KB §17;
* forensic-звітів (вони живуть у `docs/observability/` або `docs/release/`).

## Конвенція іменування

```
docs/backlog/<task-slug>.md
```

* `<task-slug>` — kebab-case, короткий і описовий.
* Приклад: `retry-policy.md`, `global-unhandled-exception.md`, `lia-cert-pinning.md`.
* Назва має співпадати з карткою-посиланням у KB §17.

## Структура файлу

```markdown
# <Назва задачі>

> Короткий опис (1–3 рядки). Посилання на картку KB §17.

## Контекст

* Чому ця задача виникла.
* Яку проблему вирішує.
* Посилання на forensic/KB-розділи, що мотивували.

## Мета (Acceptance Criteria)

* AC1: <конкретний вимірюваний критерій>
* AC2: ...
* AC3: ...

Кожен AC повинен бути перевіреним фактом (код, build, runtime, тест).

## Варіанти рішення

### Варіант A: <назва>
* Опис.
* Плюси.
* Мінуси.
* Ризики.

### Варіант B: ...

## Рекомендоване рішення

<Обраний варіант> + обґрунтування (чому KISS/Zero Regression/Reuse First).

## Зона впливу

* Файли: ...
* Сервіси: ...
* Схема БД (якщо зачіпає): ...
* Контракти (якщо зачіпає): ...

## Ризики та мітігація

| Ризик | Мітігація |
|---|---|

## Quality Gates (домен-специфічні)

* Core: Root Cause, Zero Regression, Evidence, UTF-8.
* Extended (якщо домен критичний): посилання на відповідний чеклист.

## Статус

* 🔵 PLANNED / 🟡 IN PROGRESS / ✅ DONE / ❌ REJECTED
* Дата останнього оновлення.
```

## Правила

1. **Єдине джерело істини** — KB §17 залишається індексом. Файл тут — деталізація.
2. **Не дублювати** — якщо інформація вже в KB/forensic, посилатися, не копіювати.
3. **Стан** — кожен файл має маркер стану (PLANNED/IN PROGRESS/DONE/REJECTED).
4. **Після завершення** — оновити картку KB §17 (перенести до Implemented або залишити з ✅), файл не видаляти (історія рішень).
5. **При відхиленні** — перенести до KB §15 (Rejected), файл залишити з ❌-маркером.
6. **Українська мова** — усі файли українською, UTF-8 (AGENTS.md «Правила кодування тексту (P0)»).

## Зв'язок з SEW

Файл у `docs/backlog/` — це артефакт етапів **Proposal + Design** SEW-циклу (див. AGENTS.md «Розширений цикл розробки»). Він замінює окремі Proposal.md/Design.md (OpenSpec/Spec Kit стиль) єдиним документом, узгодженим зі стилем SCLOC-Verse.
