# SCLOC-Verse Development Rules

Ти працюєш над проєктом SCLOC-Verse.

Перед початком роботи врахуй результати форензик аналізу архітектури, історії Git, стилю автора та структури проєкту.

---

# Єдина база знань (Single Source of Truth)

Перед будь-якою роботою ОБОВ'ЯЗКОВО:

1. Спочатку читати `docs/SCLOCVerse-Knowledge-Base.md`.
2. Якщо відповідь є там — НЕ перечитувати десятки forensic-документів і НЕ виконувати повторних досліджень.
3. Лише якщо відповіді в KB немає — звертатись до першоджерел (список у розділі 18.1 KB).

## Knowledge Base — живий документ

`docs/SCLOCVerse-Knowledge-Base.md` є Single Source of Truth і постійно підтримується в актуальному стані. Заборонено не редагування документації, а дублювання інформації та створення нових документів для вже описаних підсистем.

Під час будь-якої реалізації дозволено:
- додавати нові знання;
- оновлювати застарілі розділи;
- видаляти інформацію, яка більше неактуальна;
- переносити задачі між Backlog / Approved Decisions / Rejected Decisions / Technical Debt / Implemented;
- додавати нові архітектурні рішення;
- оновлювати схеми після реалізації;
- виправляти неточності;
- позначати реалізовані задачі як завершені.

Заборонено лише одне: **Не створювати нових документів, якщо інформація вже належить до існуючої Knowledge Base** (наприклад, Telemetry-Optimization-v2.md, New-Architecture-Review.md, Forensic-After-Fix.md). Натомість оновлюється відповідний розділ KB.

Створення нового документа допустиме лише для абсолютно нової підсистеми, якої немає в KB (наприклад: Plugin SDK, Cloud Sync, Marketplace, Linux Version).

KB відображає поточний стан системи, а не накопичує історію змін: після реалізації задачі — переносити з Backlog до Implemented / Approved Decisions / Rejected Decisions, а не залишати як журнал змін.

## Knowledge Base Synchronization (після кожної фази та кожного forensic)

**Жодна реалізація не вважається завершеною, доки Knowledge Base не синхронізована.**

**Будь-який forensic, який змінив хоча б один архітектурний висновок, рішення або припущення, ОБОВ'ЯЗКОВО завершується KB Synchronization до наступної роботи.**

Після завершення кожної фази (або погодженого етапу) **або після forensic-аудиту, що підтвердив/спростував гіпотезу** ОБОВ'ЯЗКОВО виконати **Knowledge Base Synchronization** — оновити `docs/SCLOCVerse-Knowledge-Base.md`, перенісши:

- **нові підтверджені факти** → відповідні розділи (2–13);
- **спростовані гіпотези** → розділ 15 (Rejected Decisions) з доказом спростування;
- **нові погоджені рішення** → розділ 14 (Approved Decisions);
- **новий технічний борг** → розділ 16 (Technical Debt);
- **нові задачі** → розділ 17 (Backlog);
- **корисну trivia** → розділи 2–13 (наприклад, lifecycle об'єктів, dependency graph);
- за потреби — оновити архітектурні розділи (2–13), якщо фаза змінила схему, SQL, телеметрію, app_installations, Control Center або Observability.

**Чому це критично:** без синхронізації наступний агент відкриє KB, побачить застарілу гіпотезу (наприклад, «`error_message` — кандидат на merge» або «`retry_count` — видалити»), і все почнеться спочатку. KB має залишатися єдиним джерелом істини.

Синхронізація виконується в тому ж робочому сеансі, що й forensic/реалізація, окремим комітом з повідомленням виду:

```
KB Synchronization: <назва фази або forensic>
```

Мета: через пів року будь-який агент відкриває один файл і бачить **поточний** стан проєкту, а не стан на момент створення документа.

## Стани forensic-знахідок (Hypothesis → Verified → Implemented)

Кожна знахідка в Knowledge Base маркується станом підтвердженості:

- 🔵 **HYP (Hypothesis)** — неперевірена гіпотеза, припущення, кандидата на перевірку.
- 🟢 **VER (Verified)** — доведено фактом (жива БД, C# код, EXPLAIN ANALYZE, git blame).
- ✅ **IMPL (Implemented)** — реалізовано в коді/схемі (Verified + внесено в систему).
- ❌ **REJ (Rejected)** — спростовано доводом (Verified False → переноситься в §15).

**Приклад:**
- `retry_count` — HYP (було «дубль») → VER (заготовка під Retry Policy) → IMPL (коли Retry Policy з'явиться).
- `error_message duplicate` — HYP → VER False → REJ.

Це дозволяє агентам бачити **ступінь підтвердженості** знань, а не лише сам факт.

## Post-Implementation Forensic (після кожної реалізованої фази)

Після кожної реалізованої фази (або міграції в production) ОБОВ'ЯЗКОВО виконати **Post-Implementation Forensic** — коротку перевірку 5–10 хвилин:

- чи **реально змінилося** те, що планувалось (snapshot до/після: schema, indexes, views, row counts);
- чи **не зламалося** щось інше (EXPLAIN ANALYZE ключових запитів, контракти views, C# SQL);
- які **припущення підтвердилися**, які **спростувалися**;
- чи потребують оновлення розділи KB (Hypothesis → Verified/Implemented/Rejected).

Не новий аудит на 100 сторінок. Лише перевірка факту.

**Одразу після** — Knowledge Base Synchronization (див. правило вище).

Цикл розробки:

```
Forensic → KB → Рішення → Реалізація → Verification → Post-Impl Forensic → KB
```

## Backup стратегія перед production-міграціями

Жодна міграція не виконується напряму в production без:

1. **Snapshot/Backup production** (Supabase Dashboard, `pg_dump`, або Point-in-Time Recovery).
2. **Тестовий deployment**: окремий Supabase project (free tier — до 2 активних) або Supabase Branching (Pro+).
3. **Post-Implementation Forensic на тестовому** середовищі.
4. **Лише потім** — production deployment.

Additive-only міграції з підготовленим rollback-скриптом — також обов'язкові.

## Rollback-скрипт (обов'язковий для кожної міграції)

Поруч із кожною міграцією `<timestamp>_<name>.sql` існує `<timestamp>_<name>.rollback.sql` — писаний **ДО** застосування міграції. Навіть якщо він ніколи не знадобиться.

Rollback не порушує additive-only політику розробки (ми не робимо DROP у фічі-міграціях), але є аварійною процедурою відкату при виявленні критичної проблеми в test/production.

## Migration Review (self-check перед виконанням)

Після написання міграції, **ДО її виконання**, обов'язково виконати **Migration Review** — самоперевірку власного SQL на:

- ідемпотентність (`IF EXISTS` / `IF NOT EXISTS`);
- конфлікти з CHECK / FK / UNIQUE constraints;
- **IMMUTABLE вимоги** для generated columns (`to_char(ts,…)` → STABLE, не підходить; використовувати `EXTRACT`);
- порядок залежностей (DROP VIEW перед DROP COLUMN; CREATE OR REPLACE для VIEW не змінює порядок колонок);
- типи даних (generated column зберігає тип виразу);
- повноту rollback-скрипта (відкатовує всі зміни міграції).

Лише після Migration Review міграція переходить зі статусу «готова до застосування» у «готова до незалежного тестування на test проєкті».

# SEW — SCLOC-Verse Engineering Workflow

> SEW — це **розширення** «Обов'язкового порядку роботи» вище, а не заміна.
> 8-кроковий цикл (Форензик → План → Погодження → Резервний commit → Реалізація → Звіт → Фінальний commit)
> залишається основою. SEW додає Quality Gates, Acceptance Criteria, Security Review, ADR та Retro.
>
> SEW базується на практиках OpenSpec, Spec Kit, BMAD, але **не є їх копією** — це внутрішня методологія,
> адаптована під одноосібну розробку, WPF/.NET, ручну композицію та Knowledge Base.
> Заборонено використовувати зовнішні CLI (OpenSpec CLI, Specify CLI, BMAD CLI). Лише Markdown та існуюча інфраструктура.

## Принципи

* **Evidence First** — рішення спираються на доказ. Без доказу — це гіпотеза (маркується HYP, див. розділ «Стани forensic-знахідок»).
* **Root Cause First** — спочатку знайти першопричину. Симптоми не лікувати.
* **Zero Regression** — зміна не погіршує існуючу поведінку (див. «Основний принцип»).
* **Forensability** — будь-яка зміна залишає слід, достатній для діагностики інциденту з платформи (Конституція Observability, Стаття 9). Це НЕ вимагає observability у кожній фічі (Стаття 1/10 — телеметрія чистий спостерігач), а вимагає можливості форензику.
* **Reuse First** — перед новим кодом довести, що аналогічне рішення вже не існує (див. «Правила розширення існуючого коду»).
* **Minimal Change** — змінювати лише те, що безпосередньо необхідне. Без «заодно».
* **Evolution over Revolution** — архітектура еволюціонує поступово (див. «Основний принцип» та «Архітектурні правила»).
* **Self-Critique** — перед завершенням критично оцінити власне рішення (чи простіше/безпечніше рішення існує?).
* **KISS / DRY** — простота та відсутність дублювання (див. «Правила коду»).

## Ієрархія інженерних пріоритетів

При конфлікті рішень керуватися ранжованим порядком. Жоден нижчий рівень не може порушувати вищий.

```
Рівень 1 — Безпека:        Безпека → Докази → Root Cause
Рівень 2 — Стабільність:   Zero Regression → Reuse First → Minimal Change
Рівень 3 — Зручність:      KISS → DRY → Автономність → Продуктивність → Естетика коду
```

## Розширений цикл розробки (SEW)

SEW розгортає 8-кроковий цикл AGENTS.md у повний цикл. Етапи, що вже існують (Backup Commit, KB Synchronization, Commit), не дублюються — посилаються на відповідні розділи.

```text
Request
    ↓
Forensic (розділ «Форензик аналіз задачі»)
    ↓
Evidence (збирання доказів: код, БД, логи, EXPLAIN)
    ↓
Proposal (що змінюємо та чому)
    ↓
Design (як змінюємо: точки інтеграції, залежності)
    ↓
AEC Review (якщо зачіпає архітектуру/БД/публічний API)
    ↓
Approval (очікування погодження користувачем)
    ↓
Backup Commit (розділ «Git правила»)
    ↓
Implementation
    ↓
Verification (build, тести, runtime-перевірка)
    ↓
Quality Gates (див. Quality Gates нижче)
    ↓
Security Review (тільки за тригером домену — див. Security Review)
    ↓
Acceptance (Acceptance Criteria виконані)
    ↓
KB Synchronization (розділ «Knowledge Base Synchronization»)
    ↓
ADR (за потреби — див. ADR)
    ↓
Commit (розділ «Git правила»)
    ↓
Retro (див. Retro)
```

## Quality Gates

Чеклист з двома рівнями. Повний опис: [`docs/checklists/Quality-Gates.md`](docs/checklists/Quality-Gates.md).

### Core Gates — обов'язкові для всіх змін

* **Root Cause Gate** — причина підтверджена доказом; симптоми не лікуються; альтернативні причини перевірені.
* **Zero Regression Gate** — існуюча поведінка не змінилась; build 0 warnings; стабільний код не зачеплено без потреби.
* **Evidence Gate** — висновок ≠ факт; HYP/VER/IMPL/REJ-маркери (розділ «Стани forensic-знахідок»); посилання на код/БД/коміт.
* **UTF-8 Gate** — українські тексти UTF-8 без mojibake (розділ «Правила кодування тексту (P0)»).

### Extended Gates — лише для критичних доменів (БД/Auth/Installer/Network/Supabase/API)

* **Simplicity / Anti-Abstraction Gate** — немає зайвих абстракцій; рішення найпростіше; без IoC/Generic Host/фабрик без погодження (див. «Архітектурні правила»).
* **Integration First Gate** — описати точку інтеграції, залежності, вплив на систему.
* **Security Review Gate** — див. Security Review нижче.

Прецедент: [`docs/checklists/Database-Verification.md`](docs/checklists/Database-Verification.md) вже реалізує Extended Gates для БД-домену.

## Acceptance Criteria (AC)

Кожна нетривіальна задача містить явні Acceptance Criteria (AC1, AC2, ...). Задача не завершена, доки всі AC не перевірені. Для тривіальних правок (опечатка, UI-твік) AC може бути одне.

AC формуються на етапі Proposal/Design, до реалізації.

## Security Review

Виконується лише якщо зміна стосує домени з тригер-списку. Чеклист: [`docs/checklists/Security-Review.md`](docs/checklists/Security-Review.md).

**Тригери Security Review:**

OAuth, Auth, Installer, Auto Update, Network, Registry, File System, SQL, Supabase, API, RLS, криптографія.

Для звичайних UI або локалізації Security Review **не потрібне**.

## ADR — Architecture Decision Records

Канонічний файл: [`ARCHITECTURE_DECISIONS.md`](ARCHITECTURE_DECISIONS.md).

Формат (існуючий): **Контекст → Рішення → Наслідки**.
SEW розширює формат: **Проблема → Контекст → Варіанти → Прийняте рішення → Наслідки** (для складних рішень).

ADR створюється для важливих архітектурних рішень. Не для кожної задачі.

## Exit Criteria (визначення «завершено»)

Задача не вважається завершеною, доки не виконано:

* реалізація;
* перевірка (build + runtime/тести);
* Acceptance Criteria всі виконані;
* Core Quality Gates пройдені (Extended — за доменом);
* Security Review (якщо тригер спрацював);
* KB Synchronization (див. відповідний розділ);
* Self-Critique проведено;
* ADR (за потреби);
* фінальний commit (розділ «Git правила»).

## Retro

Після завершення значущої функції або приблизно раз на місяць проводити ревізію:

* що в процесі працює;
* що зайве (які Gates прибрати);
* що варто автоматизувати;
* що сповільнює процес.

Retro не створює окремий артефакт — фіксується через оновлення KB §16 (Technical Debt) та §17 (Backlog): видалення застарілого, перенесення завершених задач, позначення нових.

## Правило невизначеності

Агент чітко розрізняє:

* Підтверджений факт (VER / IMPL).
* Висновок (з маркером доведеності).
* Припущення (HYP).
* Гіпотеза (HYP).
* Особиста рекомендація (позначається явно).

Заборонено подавати припущення як підтверджений факт. Див. розділ «Стани forensic-знахідок».

## Правило завершеності

Задача завершена лише якщо:

* виконані Acceptance Criteria;
* пройдені необхідні Quality Gates;
* проведено Self-Critique;
* оновлено Knowledge Base;
* оцінені можливі регресії;
* немає неперевірених критичних припущень.

## Автономність та її межі

Агент максимально автономний у межах підтверджених фактів та затверджених правил.

**Дозволено самостійно:** досліджувати кодову базу, знаходити точки інтеграції, аналізувати залежності, шукати першопричину, перевіряти KB/AGENTS.md/Constitution, проводити форензик, формувати варіанти рішень.

**Питання дозволені лише якщо:** відсутні необхідні дані; існує кілька рівнозначних варіантів; потрібне рішення, що змінює поведінку продукту. Заборонено питання, відповідь на які можна знайти аналізом коду/KB.

**Автономність НЕ означає право самостійно:** змінювати архітектуру, виконувати глобальні рефакторинги, змінювати публічний API, змінювати схему БД, змінювати правила безпеки, виконувати незворотні дії, створювати/видаляти файли всупереч процесу. У таких випадках — зупинка після форензик-аналізу та очікування погодження.

# Правила кодування тексту (P0)

Це критичне правило. Пошкодження українського тексту (mojibake) не допускається ні в коді, ні в релізних артефактах, ні в GitHub API.

## Джерела ризику

* PowerShell за замовчуванням використовує кодування консолі (часто Windows-1251 або OEM), а не UTF-8.
* `Invoke-WebRequest -Body $string` кодує тіло запиту в кодуванні консолі, яке GitHub API не розуміє для українських символів.
* `Out-File`, `Set-Content` без `-Encoding UTF8` можуть записати файл у Windows-1251.
* `File.ReadAllText` без явного `Encoding.UTF8` на системі з не-UTF8 локаллю прочитає файл неправильно.
* Редактори, які зберігають XAML/JSON/C# файли без BOM або в ANSI, псують українські символи.

## Обов'язкові вимоги

1. **Всі C# / XAML / JSON / .iss / .ps1 файли** мають бути збережені у **UTF-8**.
2. **Усі українські тексти в коді** мають бути UTF-8 з коректними кодами символів, без mojibake (`Р›Р°СЃРєР°РІРѕ`, `??????` тощо).
3. **Читання текстових файлів** виконувати тільки з явним `Encoding.UTF8`:
   ```csharp
   File.ReadAllText(path, Encoding.UTF8)
   await File.ReadAllTextAsync(path, Encoding.UTF8)
   new StreamReader(path, Encoding.UTF8)
   ```
4. **Запис текстових файлів** виконувати тільки з явним `Encoding.UTF8`:
   ```csharp
   File.WriteAllText(path, content, Encoding.UTF8)
   await File.WriteAllTextAsync(path, content, Encoding.UTF8)
   ```
5. **PowerShell — запис файлів**:
   ```powershell
   $content | Set-Content -Path $file -Encoding UTF8
   [System.Text.Encoding]::UTF8.GetBytes($content) | Set-Content -Path $file -Encoding Byte
   ```
6. **PowerShell — веб-запити з JSON**:
   ```powershell
   $json = @{ body = "Український текст" } | ConvertTo-Json
   $bytes = [System.Text.Encoding]::UTF8.GetBytes($json)
   Invoke-WebRequest -Uri $url -Method POST -Body $bytes -ContentType "application/json; charset=utf-8" -Headers @{ ... }
   ```
   Ніколи не передавати український текст в `-Body $string` напряму.
7. **GitHub API release notes** створювати/оновлювати тільки з UTF-8 байтами та заголовком `Content-Type: application/json; charset=utf-8`.

## Перевірка перед commit / релізом

* Запускати `dotnet build` та візуально перевіряти всі екрани з українським текстом.
* Перевіряти GitHub release notes в браузері одразу після публікації.
* Якщо знайдено `Р›Р°СЃРєР°РІРѕ`, `Ð›Ð°`, `??????` — це P0 регресія, виправляти негайно.

## Наслідки порушення

* Пошкоджений український текст у продукті = P0 дефект.
* Пошкоджені release notes = непрофесійний публічний реліз.
* Mojibake в commit історії ускладнює подальшу роботу з кодом.

# Архітектурні правила

Поточна архітектура є базовою та приймається без глобальних змін.

Заборонено:

* переписувати проєкт на іншу архітектуру;
* впроваджувати MVVM-фреймворки;
* впроваджувати сторонні IoC-контейнери;
* додавати складні патерни без необхідності;
* виконувати глобальний рефакторинг без погодження.

Використовувати існуючий підхід:

* AppCompositionRoot;
* ручна композиція залежностей;
* функціональне групування папок;
* Canvas-підхід;
* існуючий стиль XAML.

# Правила коду

Код:

* тільки англійською мовою;
* професійний C#;
* .NET 9;
* Nullable Enabled;
* DRY;
* KISS;
* SOLID без фанатизму.

Коментарі:

* тільки українською мовою.

Документація:

* українською мовою.

# Async правила

Async методи:

* обов'язково суфікс Async;
* CancellationToken додавати де це доцільно.

У сервісах використовувати `ConfigureAwait(false)` там, де це дійсно потрібно.
Не додавати `ConfigureAwait` механічно.

У UI-шарі використовувати стандартний `await`, якщо немає спеціальної причини для іншої поведінки.

Не використовувати async void окрім обробників подій WPF.

# Правила розвитку проєкту

Не збільшувати відповідальність MainWindow.xaml.cs без необхідності.

Нову логіку по можливості розміщувати:

* у сервісах;
* у відповідних Canvas;
* у допоміжних класах.

Не переносити існуючу логіку між шарами без погодження.

Не виконувати рефакторинг лише заради "кращих практик".

---

# Правила розширення існуючого коду

Не створювати нові файли без необхідності.

Не створювати нові сервіси, інтерфейси або моделі, якщо існуючі вже вирішують задачу.

Перевага віддається розширенню існуючого коду.

Перед написанням коду завжди аналізувати існуючу реалізацію.
Якщо схожа логіка вже існує в проєкті — використовувати існуючий підхід автора.
Не вигадувати нову реалізацію, якщо аналог вже є.

---

# Правила стабільного коду

Якщо файл:

* давно не змінювався;
* не має відкритих дефектів;
* працює стабільно,

вважати його стабільним.

Не змінювати без прямої необхідності.

# Правила виправлення помилок та неймінгу

Опечатки необхідно виправляти.

Перед виправленням визначити:

* чи використовується назва публічно;
* чи є зовнішні залежності;
* чи не виникне регресія.

Якщо ризик мінімальний:

* виправити.

Якщо ризик підвищений:

* провести форензик аналіз;
* показати ризики;
* отримати погодження.

Не залишати очевидні помилки типу:

* Resul → Result
* Cash → Cache
* Setupe → Setup
* Instal → Install
